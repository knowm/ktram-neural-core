# The lane read on edge CPU

Generated by the 08d measurement pass, 2026-07-31; regenerate with
`benchmarks/bench_lane_read.py` (sections: race / conditional / crossover).
Host: Intel i9 (10 cores), macOS, torch 2.2.2, 10 threads, no CUDA. Every lane-read variant
passed the bit-exact gate against `_lane.read_sums` — int32 sums and float64 `y` identical —
before its time counted. The 08a battery (115 tests, including the two new throughput floors)
is green on the shipped default read.

## 1. The race

The lane read is an embedding bag, not a GEMM: `read_sums` gathers one int8 value per active
space, indexed by symbol, and sums. The race timed four formulations of that read on identical
inputs (index build + gather + sum + divide; the rank-cut/argmax post step is shared by every
variant and timed once per shape), plus dense controls at the matched shape `[B, 2k] @ [2k, L]`
— the op the lane replaces, not a read.

- **incumbent** — the previous masked gather-and-sum, which materializes a `[L, B, K]` int32
  intermediate (batch-chunked here so it fits in memory).
- **bag-fp32** — `F.embedding_bag(mode='sum')` over a `[k·S + 1, 2L]` float32 table, diff and
  mag side by side, one all-zero row so NONE needs no masking branch. Exact: the sums are
  integers far below 2^24, where float32 arithmetic is exact.
- **fbgemm-i8** — `torch.ops.quantized.embedding_bag_byte_rowwise_offsets` on hand-fused byte
  rows (uint8 = int8 + 128, per-row scale 1.0, bias −128.0): DLRM's `SparseLengthsSum` kernel
  running on (nearly) our frozen pack bytes.

Median vectors/sec; regenerate the full tables with `bench_lane_read.py --section race`.
The two `—` cells were skipped after the S=64 shape pinned the incumbent's rate (it chunks
internally, so it scales linearly in B).

**The winner.** FBGEMM's int8 embedding bag on the frozen tier, the float32 bag on the live
tier. Against the incumbent: 3–10× at the generator's real shapes, 67–130× at transformer
shapes (the incumbent's `[L, B, K]` intermediate is the whole problem — at k=512, L=1024 it
forces tiny batch chunks and re-streams the bank per chunk). The default `read` now runs on
this formulation on CPU (cached table, rebuilt after any `adapt`; non-CPU devices and the
fresh reads inside `adapt` keep the exact gather — MPS has no `embedding_bag` in this torch).
One-time table builds cost 0.3 ms (encoder) to 220 ms (transformer live tier).

**The headline ratio, against the dense int8 control:**

| shape | B=1 | B=65536 |
|---|---:|---:|
| decoder [1568, k16, S64] | 6.2× slower | 23.6× slower |
| xfmr [1024, k512, S64] | 5.4× slower | 16.0× slower |
| xfmr [1024, k512, S16] | 4.5× slower | 8.3× slower |

Reading those honestly: the read does the same number of elementary operations as the dense
control (k·2L adds vs 2k·L multiply-adds), so the whole gap is memory behavior, and it
decomposes into three parts. (1) A GEMM streams its weights once per batch and amortizes;
a gather reads k private rows per vector, so at batch it saturates DRAM instead of compute —
the fbgemm rows sit at ~17 GB/s, this host's bandwidth. That part is inherent to the op on
digital hardware. (2) The dense control's 1–4 MB weight matrix stays cache-resident for the
whole timing loop while our S×-inflated table (17–268 MB) streams; a full multi-layer model
evicts the dense weights too, so the single-layer bench flatters the control — the B=1
column, where dense must also stream everything per token, is the representative one for
generation. (3) Threading is NOT the gap: forcing the bag onto 1 vs 10 threads changes it
only 1.4× (5.1k → 7.2k vec/s at the S=64 transformer shape), and a manual batch split
across cores — which the AAT structure makes static and lock-free — plateaus at the same
ceiling by 4 threads. The read is bandwidth-bound; the GEMM is compute-bound, which is why
cores multiply the control and merely queue for us. The levers that move the read are all
byte levers: int8 rows (4×, shipped), S=16 (the 8.3× column), and active-count sparsity
(§2) — the 08e SIMD profile starts from there, plus a lane-banded split for B=1 latency.
What remains after the byte levers is the memory bus itself, which is the hardware thesis
measured: on digital hardware every read moves the table; on kT-RAM the table is the
substrate and does not move.

## 2. Conditional compute

RankCut output sparsity is structured by construction: whole spaces go quiet, and −1 is
already native in the read. Two measurements, both gated bit-exact:

**Fire rates through the lane bridge.** The digits pipeline (codec → 10-lane Classifier,
Vt = 0) fires a mean **21.1%** of lanes per read (p10 10%, p90 30%) at 0.887 test accuracy.
A fired-lane output AAT is the next stage's input AAT, so ~21% is the active fraction a
second lane stage would see. (The 08c two-stage stack extends this measurement once it
exists.)

**Read cost vs active-space count** (B=4096, frozen tier, offsets-form bag that drops NONE
entries; the fixed-shape bag tracks it because NONE rows stay cache-hot):

| xfmr [1024, k512, S64] | n=32 | n=64 | n=128 | n=256 | n=512 |
|---|---:|---:|---:|---:|---:|
| varlen bag (vec/s) | 42,901 | 30,615 | 18,574 | 9,750 | 6,518 |
| lane bytes/vector | 64K | 128K | 256K | 512K | 1M |
| dense int8 (vec/s) | 312,268 | 312,265 | 314,097 | 235,931 | 327,452 |

Wall clock follows the active count: 1/16 of the spaces active is 6.6× the throughput. The
dense control is flat — a dense layer cannot skip anything. At the decoder shape the curve
is flat for the lane too (the 3 MB table is cache-resident and per-call overhead dominates);
conditional sparsity converts to wall clock where the table outgrows cache, which is exactly
the regime that matters. The multiplicative effect at the measured 21% fire rate, transformer
shape: ~0.21 × 2kL bytes ≈ 220 KB touched per vector vs the dense layer's fixed 1 MB — about
4.8× fewer bytes on top of whatever the codec already saved, with ~4–5× of it showing up as
measured wall clock.

## 3. The streaming-vs-batched adapt crossover

Both `adapt` paths at the generator's module shapes, per backend (full tables in
`bench_lane_read.py --section crossover` regenerates the full tables):

- **Classifier [10, k16, S64], CPU:** batched passes streaming at **B=2** and scales to
  ~47,000 ex/s at B=256 (38× the streaming rate, which holds ~1,250 ex/s at any B). The 08a
  tier-3 band qualifies B=16 (label accuracy within 0.1 of serial); larger B is unqualified
  territory quality-wise, not speed-wise.
- **BasisEncoder [16×64, k49, S2], CPU:** the batched path's per-example bookkeeping keeps it
  behind streaming until **B≈16–32** (322 vs 297 ex/s at B=16; 413 vs 180 at B=32), and it
  plateaus near ~410 ex/s. The tier-3 utilization/entropy bands hold through B=64, so the
  whole beneficial range is qualified.
- **MPS:** the two modules split. The classifier is dispatch-bound at this tiny size —
  batched reaches 18,702 ex/s at B=256, still 2.5× under CPU, and streaming runs at 76 ex/s
  (16× under CPU). The encoder is the opposite: its batched crossover lands at **B=2** on
  MPS and reaches **4,205 ex/s at B=256 — 11.6× the CPU batched path**, because the heavy
  per-group scatter runs on the GPU while CPU stays stuck behind it. (This measurement first
  threw on MPS for B≥2 — batched encoder adapt was indexing non-CPU buffers with CPU index
  tensors — and that bug is now fixed; the rates above are from the fixed path. The full
  GPU answer still belongs to 08f.)

## 4. Throughput floors

`tests/test_lane_read_floors.py` pins two ratios, measured in the same run on the same host,
never absolute rates: the default read must run at least **2×** the masked-gather formulation
(measured ~10×), and within **100×** of the matched dense fp32 GEMM (measured ~30×). The
spot-check monkeypatches the default read back to the masked gather
and both floors trip; on the real kernel both pass.

## 5. Packaging

`pip install ktram-neural-core[torch,examples]` into a clean venv **found a real break**: pip
resolves numpy 2.4.6 next to torch 2.2.2 on Intel macs (the last torch published for that
platform, built against numpy 1.x), and `torch.from_numpy` fails with "Numpy is not
available". Fixed with a platform-marked pin in the `torch` extra
(`numpy<2; sys_platform == 'darwin' and platform_machine == 'x86_64'`). After the pin: clean
install resolves numpy 1.26.4, the import line works, and the lane-bridge example runs end
to end in the fresh venv (0.887 test accuracy on the held-out digits, matching the repo
venv).

## 6. The two open questions from spec 08 §10, answered with numbers

**The compute layout.** One row per (space, symbol) pair with the lane axis contiguous, read
by an embedding-bag gather, wins everywhere: 3–10× over the `[L, B, K]` masked gather at the
generator's shapes and 67–130× at transformer shapes. The gather-rows layout is now the
default CPU read.

**Whether int8-GEMM ever beats gather-and-sum.** No. The one-hot lift hands a GEMM an inner
dimension of k·S against the dense control's 2k — S/2× the work — so the measured dense-int8
rates upper-bound the lifted GEMM at 248,642/32 ≈ 7.8k vec/s (S=64) and 283,560/8 ≈ 35.4k
(S=16) at B=4096, against fbgemm's measured 19.6k and 37.9k on the same inputs. The GEMM
never recovers the lift even at its own best batch size, and the gap widens with S. The GEMM
was never the right kernel family for this op; the right family is the one recommendation
systems already optimized — int8 embedding bags — and its per-row-scale format is nearly our
frozen pack.
